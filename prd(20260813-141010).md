# LightningRAG — Product Requirements Document

## 1. Product Overview

**LightningRAG** is a small validation project whose purpose is to test `LightningParse` as the PDF ingestion layer of a Retrieval-Augmented Generation (RAG) pipeline.

The project is deliberately small in its first version. It is not intended to become a production RAG platform, benchmark framework, or agentic system.

The first milestone is:

> Parse one difficult PDF with LightningParse, build a minimal RAG pipeline around the extracted structure, ask five questions, and manually verify the results.

## 2. Problem

PDF documents are visually structured but are often difficult for downstream RAG systems to process reliably.

Problems include:

- Multi-column reading order
- Headings and section boundaries
- Tables
- Page metadata
- Headers and footers
- Long-form book structure
- Scanned pages and OCR
- Loss of context during chunking

LightningParse is intended to provide a structured, high-performance PDF parsing layer.

LightningRAG will test whether that structured output is actually useful when fed into a real RAG pipeline.

## 3. Goals

### Primary Goal

Validate that LightningParse can provide useful input for a small PDF-based RAG system.

### Secondary Goals

- Inspect LightningParse's actual output.
- Verify two-column reading order.
- Verify section and page metadata.
- Test table extraction.
- Build metadata-aware chunks.
- Generate embeddings.
- Store embeddings in FAISS.
- Retrieve relevant chunks.
- Generate answers with an LLM.
- Return source/page information.
- Manually evaluate five questions.

## 4. Non-Goals for v0.1

The first version must NOT attempt to build:

- A production RAG platform
- A large-scale benchmark suite
- Automated evaluation infrastructure
- A parser comparison framework
- An agent system
- A multi-vector-database abstraction
- A distributed ingestion system
- A complex frontend
- A LangChain-based orchestration layer
- Automated Recall@k evaluation

These may be considered after v0.1 succeeds.

## 5. Target Users

The project is primarily a developer/research validation tool.

The intended user should be able to:

1. Provide a PDF.
2. Parse it with LightningParse.
3. Build an index.
4. Ask questions.
5. Inspect retrieved evidence.
6. Verify the answer against the source PDF.

## 6. Initial Technology Stack

- Python
- LightningParse
- Sentence Transformers
- FAISS
- LLM API or local LLM
- Optional Streamlit UI

Avoid LangChain in v0.1 so that the data flow remains explicit.

## 8. Functional Requirements

### FR-01 PDF ingestion

The system shall accept a PDF path.

### FR-02 Parsing

The system shall parse the PDF using LightningParse.

### FR-03 Structure inspection

The system shall expose page and block information for debugging.

### FR-04 Metadata preservation

Each RAG chunk shall preserve at least:

- Source filename
- Page number
- Section identifier when available
- Chunk text

### FR-05 Chunking

The system shall convert parsed blocks into retrieval-ready chunks.

### FR-06 Embeddings

The system shall generate embeddings using a Sentence Transformers model.

### FR-07 Vector search

The system shall store and retrieve embeddings using FAISS.

### FR-08 Question answering

The system shall pass retrieved context to an LLM.

### FR-09 Source attribution

The final response shall identify the source document and page for retrieved evidence.

### FR-10 Manual evaluation

The system shall support a fixed set of five questions with expected answers and source locations.

## 9. Initial Documents

The first test corpus shall contain:

1. A synthetic two-column PDF specifically created to test PDF structure.
2. One real book PDF supplied by the developer.

The synthetic document should include:

- Two columns
- Headings
- Subheadings
- Dense paragraphs
- A table
- Repeated terminology
- Multiple pages

## 10. Quality Requirements

The parser output should be inspected before RAG is implemented.

Important checks:

- Reading order is coherent.
- Text from columns is not incorrectly interleaved.
- Sections are identifiable.
- Page numbers are retained.
- Tables are not silently discarded.
- Chunks contain coherent semantic units.
- Retrieved chunks can be traced back to the source.

## 11. v0.1 Success Criteria

The MVP is successful if:

- LightningParse processes the synthetic PDF.
- Two-column reading order is reasonably correct.
- Headings and sections are recoverable.
- Table content is recoverable.
- Metadata survives chunking.
- FAISS returns relevant chunks.
- The LLM can answer questions from retrieved context.
- Source/page information is returned.
- At least 4 of 5 manually authored questions are answered correctly.
- The same pipeline works on one real book PDF.

## 12. Design Principle

Keep the first implementation transparent.

Prefer:

```text
LightningParse -> Python objects -> chunks -> embeddings -> FAISS -> LLM
```

over:

```text
LightningParse -> multiple abstraction frameworks -> hidden pipeline
```

The purpose is to understand LightningParse's contribution before introducing additional abstractions.
